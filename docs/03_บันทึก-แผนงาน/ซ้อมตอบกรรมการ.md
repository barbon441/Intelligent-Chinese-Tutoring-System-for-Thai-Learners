# 🎤 บทซ้อมตอบกรรมการ — ชุดคำถาม Tech + Product (7 ข้อ)

> จากเซสชันซ้อมของบอล 22 ก.ค. 2026 · ใช้ซ้อมก่อนสอบ midterm/ปลายภาค · ตะวันใช้ซ้อมได้ด้วย
> วิธีซ้อม: อ่านคำถาม → ตอบปากเปล่าเองก่อน → ค่อยเปิดเฉลยเทียบ

## 🏆 5 กฎทองตอบคำถามเทค
1. **เริ่มจากคำสากล → ค่อยเจาะชื่อเครื่องมือ** ("JavaScript ครับ... เขียนผ่าน TypeScript")
2. **ตอบให้ครบทุกท่อนของคำถาม** (จุดโดนหักคะแนนบ่อยสุดคือลืมท่อนหลัง)
3. **ห้ามพูด "ML/AI" ลอย ๆ** — ต้องตามด้วยชื่อจริง + หลักการ 1 ประโยคเสมอ
4. **เลขทองพูดทุกครั้ง:** 300 คำ (HSK1 3.0) · สเกล 200 ผ่าน 120 · "ตรวจด้วยเฉลยตายตัว ไม่ใช้ AI เดา"
5. **"งานวิจัยบอกจุด ข้อมูลผู้ใช้บอกคน"** — ห้ามเคลมเกินหลักฐาน (UI ภาษาไทยมีคู่แข่งทำแล้ว เช่น KAKA · ของที่ไม่มีใครทำ = วินิจฉัย Thai-L1 + เทรนด้วยข้อมูลคนไทย)

## ข้อ 1: "เขียนด้วยภาษาอะไร ใช้เครื่องมืออะไรบ้าง"
> "ฝั่งหน้าเว็บเขียนด้วย **TypeScript ซึ่งคือ JavaScript ที่เพิ่มระบบตรวจ type** ครับ ใช้เฟรมเวิร์ก **Next.js (React)** จัดโครงเว็บ ตกแต่งด้วย **Tailwind CSS** · ฝั่งเซิร์ฟเวอร์เป็น **Python ใช้ FastAPI** รันไลบรารี ML อย่าง pyBKT · ฐานข้อมูลใช้ **Supabase (PostgreSQL บนคลาวด์)** · deploy จริงแล้วบน **Vercel กับ Render** ครับ"

สูตรไล่ 4 สถานี: **หน้าเว็บ → หลังบ้าน → ฐานข้อมูล → deploy**

## ข้อ 2: "TypeScript ต่างจาก JavaScript ยังไง ทำไมไม่เขียน JS ตรง ๆ"
> "TypeScript คือ JavaScript ที่เพิ่ม**ระบบตรวจชนิดข้อมูล (type checking)** ครับ เช่นเผลอเอาข้อความใส่ตัวแปรตัวเลข มันเตือน**ตั้งแต่ตอนเขียน ก่อน build** ไม่หลุดไปพังต่อหน้าผู้ใช้ · โปรเจกต์ผมหลายไฟล์หลายหน้า type ช่วยกันพลาดตอนแก้ข้ามไฟล์ · สุดท้ายตอน build มันถูก **compile เป็น JavaScript** อยู่ดีครับ"

⚠️ อย่าพูด "ตรวจคำผิด" (นั่น spell checker) — พูด "ตรวจชนิดข้อมูล/type"

## ข้อ 3: "เก็บข้อมูลที่ไหน ทำไมไม่ใช้ MySQL"
> "เก็บใน **Supabase** ซึ่งข้างในคือ **PostgreSQL** ครับ — ที่เลือกเพราะมันให้มากกว่าฐานข้อมูล คือแถม**ระบบล็อกอิน (Auth) กับที่เก็บไฟล์เสียง (Storage)** บนคลาวด์ ฟรี ในบริการเดียว · ถ้าใช้ MySQL ได้แค่ตัว DB ต้องหาเซิร์ฟเวอร์รันเอง เขียนล็อกอินเอง ไม่เหมาะกับโปรเจกต์งบศูนย์ครับ"

สูตรคำถามเปรียบเทียบ: **ชม X สั้น ๆ → โจทย์เราต่างตรงไหน → ของเราตอบโจทย์นั้น** (ห้ามด่า X)

## ข้อ 4: "เว็บรันอยู่ไหน ถ้าคอมคุณปิดยังเข้าได้ไหม"
> "รันบนคลาวด์ครบชุดครับ — เว็บบน **Vercel** · API บน **Render** · ฐานข้อมูลบน **Supabase** · คอมผมปิดเว็บก็ทำงานปกติ เพราะไม่ได้รันจากเครื่องผม และทุกครั้งที่ push โค้ด ระบบ **deploy อัตโนมัติ** ครับ เดี๋ยวเปิดให้ดูเลยครับ"

⚠️ ก่อนเข้าห้องสอบ 5 นาที: เปิดเว็บ + กดปุ่มยิง API 1 ครั้ง**ปลุก Render** (ฟรีหลับหลัง 15 นาที ตื่นช้า ~30-50 วิ)

## ข้อ 5: "วัดยังไงว่าผู้เรียนพร้อมสอบ HSK1 จริง"
> "วัด 2 ชั้นครับ · **ระหว่างเรียน** — ทุกการตอบบันทึกรายทักษะ ใช้ **Knowledge Tracing (pyBKT)** ประเมินความแม่นรายทักษะเป็น % โดยไม่ต้องรอสอบ · **ตัวชี้ขาด** — Mock Exam จำลองข้อสอบ HSK1 จริงทั้งรูปแบบและเวลา ให้คะแนน**สเกล 200 ผ่านที่ 120 ตามเกณฑ์จริง** · ทุกข้อตรวจด้วยกติกาเทียบเฉลยตายตัว ไม่ใช้ AI เดา ผลจึงตรวจสอบได้ครับ"

## ข้อ 6: "Knowledge Tracing ทำงานยังไง อธิบายง่าย ๆ"
> "มันคือเทคนิคประเมินว่าผู้เรียนแม่นทักษะไหนแค่ไหน จากประวัติการตอบครับ หลักคิดเหมือน**ครูสังเกตนักเรียน** — ตอบถูกความเชื่อว่าแม่นเพิ่ม ตอบผิดก็ลด แต่ที่ฉลาดคือมันคิดเผื่อว่า **ถูกเพราะฟลุกเดา หรือผิดเพราะสะเพร่าทั้งที่รู้จริง** ด้วย ระบบเลยได้ตัวเลขความแม่นเป็น % ต่อทักษะ อัปเดตทุกครั้งที่ตอบ · ผมใช้ไลบรารี pyBKT และจุดต่างคือ**เทรนด้วยข้อมูลผู้เรียนคนไทยที่ระบบเก็บเอง** ครับ"

⚠️ ห้ามตอบว่า "เป็นสูตรที่ผู้เชี่ยวชาญคิดมาแล้วเราเรียกใช้" — คือการยอมรับว่าไม่เข้าใจของที่ตัวเองใช้
ลำดับที่ถูก: **หลักการ → เครื่องมือ (pyBKT) → จุดต่างเรา (ข้อมูลไทย)**

## ข้อ 7 (บอส): "แอปเรียนจีนมีเป็นร้อย ทำไมต้องใช้ของคุณ"
> "แอปใหญ่ดีครับ ผมไม่เคลมว่าดีกว่าเขาทุกด้าน — แต่เขา**สอนเหมือนกันทุกชาติ** ไม่รู้ว่าคนไทยพลาดตรงไหนเพราะภาษาไทย · ของเราต่าง 3 ข้อ: **หนึ่ง** วินิจฉัยจุดผิดเฉพาะคนไทย เช่น สับสนวรรณยุกต์เสียง 2/3 หรือวางคำขยายแบบไทย — รวบรวมจากงานวิจัยจริง แล้วออกแบบ**ตัวลวงข้อสอบให้บอกได้ว่าพลาดเพราะอะไร** · **สอง** โมเดลเทรนด้วย**ข้อมูลคนไทยที่เราเก็บเอง** ไม่ใช่ global · **สาม** เราเป็น**แอปติวสอบ** วัดด้วยเกณฑ์จริง 120/200 ไม่ใช่แอปเรียนเรื่อย ๆ · เหตุที่แอปใหญ่ไม่ทำ เพราะเขาต้องสเกลหลายสิบภาษา ทำเฉพาะภาษาแม่ทีละชาติไม่คุ้มสำหรับเขา — แต่คุ้มสำหรับเรา เพราะเราทำเพื่อคนไทยชาติเดียวครับ"

## โบนัส: คำศัพท์ที่ต้องนิยามได้ใน 1 ประโยค
| คำ | นิยามสั้น |
|---|---|
| JSX/TSX | ไวยากรณ์ของ React ที่ให้เขียนแท็ก HTML ปนในโค้ด (.tsx = เวอร์ชัน TypeScript) |
| React | ไลบรารีสร้าง UI เป็น component — เราเรียกใช้มัน |
| Next.js | เฟรมเวิร์กที่ครอบ React — กำหนดโครง ระบบหน้า build ให้ (มันเรียกโค้ดเรา) |
| PWA | เว็บที่ติดตั้งบนมือถือได้เหมือนแอป ใช้ผ่านเบราว์เซอร์ก็ได้ |
| FSRS | อัลกอริทึมจัดตารางทบทวน "ตอนกำลังจะลืมพอดี" (ตอบว่า *เมื่อไหร่ควรทวน*) |
| pyBKT | ไลบรารี Knowledge Tracing (ตอบว่า *แม่นแค่ไหน*) — คนละหน้าที่กับ FSRS |
| compile | การแปลงโค้ด (เช่น TypeScript → JavaScript) ก่อนรันจริง |

# 🗄️ ชุดที่ 2 — คำถามฐานข้อมูล สไตล์อาจารย์รอบ 5–7 (7 ข้อ)

> จากซ้อมผ่านมือถือ 28 ก.ย. 2026 · อาจารย์ถามเรื่องเดียวกันแทบทุกข้อ: **"เก็บใหม่ หรือคำนวณจากของเดิม"** และ **"ดูตารางไหน"**
> ผลรอบแรก: ผ่านครึ่ง 3 · บาง 2 · ไม่ผ่าน 1 · ขอเฉลย 1 → ซ้อมซ้ำข้อ 1, 3, 4, 5

## 🏆 3 กฎเพิ่มสำหรับคำถาม DB
1. **นับท่อนคำถามก่อนตอบ** — อาจารย์ถาม 2 ท่อนเสมอ (ตารางไหน + ทำไม) ตอบท่อนเดียว = โดนทวง
2. **ตอบเป็น ตาราง.คอลัมน์** — ไม่ใช่แนวคิด · ไม่แน่ใจชื่อ พูดว่า "ขอชี้ในผังครับ" **ห้ามเดาชื่อ**
3. **พูด "กฎ" ไม่ใช่ความรู้สึก** — คำที่ต้องหลุดปาก: *สถานะ ไม่ใช่ตัวนับ · ผลโมเดล ไม่ใช่การนับ · [cache] ติดป้ายชัด · 1:N ใช้ FK / M:N ใช้ตารางกลาง*

## ข้อ 1: "mastery_snapshots เก็บใหม่ หรือประเมินจากที่มีอยู่แล้ว ทำไมไม่ query เอา"
⚠️ ห้ามเปิดด้วย "เก็บใหม่ครับ" — คำนี้ทำอาจารย์เข้าใจผิดรอบ 6 ว่าเป็นตารางก๊อป attempts
> "**ประเมินจาก attempts ครับ ไม่ได้เก็บใหม่** · attempts คือบันทึกดิบว่าใครตอบข้อไหนถูกหรือผิด ส่วน mastery_snapshots คือ**ผลลัพธ์ของโมเดล pyBKT** ที่อ่าน attempts แล้วให้ค่าความน่าจะเป็นว่าคนนี้รู้ทักษะนี้แล้ว 1 แถวต่อคนต่อทักษะ · ที่ SQL สรุปเองไม่ได้เพราะไม่ใช่การนับถูกผิด แต่เป็นการอัปเดตความเชื่อทีละข้อโดยคิดเผื่อเดาถูกและสะเพร่าด้วย ต้องรันโมเดลใน Python · และหน้าจุดแข็ง/จุดอ่อนกับตัวเลือกข้อสอบต้องอ่านค่านี้ทุกครั้ง จะรันโมเดลใหม่ทุก request ไม่ไหว เลยเก็บค่าล่าสุดไว้เป็นตาราง cache ครับ"

โครง: **ประเมินจาก → ผลโมเดล ไม่ใช่นับ → SQL ทำไม่ได้เพราะ guess/slip → เก็บเพราะต้องอ่านบ่อย**
(รูปทรง "ค่าล่าสุด 1 แถว/คน×ทักษะ" ยังรอบอลเคาะ — ถ้าเคาะ พูดว่า "ปรับตามที่อาจารย์ติ")

## ข้อ 2: "skills ก็คือ ฟัง พูด อ่าน เขียน ใช่ไหม มีกี่แถว"
> "**ไม่ใช่ครับ** skills คือ**หน่วยความรู้ย่อยที่ BKT ติดตาม** 23 แถว 3 กลุ่ม: **จุดผิดคนไทย 15** (เช่น เสียง 2/3, zh/ch/sh) · **คำศัพท์รายหมวด 5** · **ทักษะรวม 3** ฟัง อ่าน เรียงประโยค · ที่ต้องละเอียดเพราะถ้ามีแค่ 'ฟัง' บอกได้แค่ฟังอ่อน แต่บอกไม่ได้ว่าอ่อนเพราะแยกวรรณยุกต์ไม่ออก ซึ่งเป็นจุดที่เราติวเจาะ · ฟัง/อ่านของข้อสอบดูที่ items.module และคะแนนรายพาร์ตใน sessions · เรื่องพูด HSK 1–2 ไม่สอบ แต่อาจารย์ให้เพิ่ม กำลังเคาะวิธีเก็บสถานะครับ"

โครง: **ไม่ใช่ → หน่วยความรู้ → 15+5+3 → ทำไมต้องละเอียด → ฟัง/อ่านอยู่ที่อื่น**

## ข้อ 3: "นาย A สอบ post แล้วยัง ดูตารางไหน แล้วรู้ได้ไงว่า pre/post ชุดเดียวกัน ไม่ใช่สุ่ม"
⚠️ รอบแรกเดาชื่อตารางที่ไม่มี — ห้ามซ้ำ
> "ดูที่ **sessions** ครับ ถ้ามีแถว kind = posttest คือสอบแล้ว 1 แถวต่อคน · เรื่องชุดเดียวกัน: แถว pre และ post มี **sessions.form_id ชี้ exam_forms แถวเดียวกัน** และรายการข้อล็อกอยู่ใน **form_items** ไม่ได้สุ่มตอนรัน ตอน post แค่สับลำดับแสดง เนื้อข้อเดิม · มี trigger กันว่า form_id ของ post ต้องเท่ากับของ pre · ข้อในชุดติดธง research_use_only ไม่ถูกหยิบไปฝึกระหว่างทางครับ"

โครง: **sessions.kind → form_id เดียวกัน → form_items ล็อกข้อ → trigger + ธงกันรั่ว**
จำ: exam_forms = **ปกชุด** (1 แถว = 1 ชุด) · form_items = **สารบัญชุด** (1 แถว = 1 ข้อในชุด: form_id, item_id, position) · items = เนื้อข้อจริง

## ข้อ 4: "นาย A เรียนหมวด 2 ถึงไหน ดูตารางไหน ทำไมไม่เขียนโค้ดนับจาก attempts"
⚠️ ตอบแค่ "query ช้า" ไม่พอ — อาจารย์จะย้อนว่า mastery_snapshots ก็ query ได้
> "ดูที่ **category_progress** ครับ คีย์ (user_id, category) มี started_at, words_learned, sentences_passed, quiz_best_score, quiz_passed_at, status · ที่ต้องเป็นตารางเพราะ**ตามที่อาจารย์บอกรอบก่อน** ว่าสถานะที่ต้องไล่ดูย้อนหลังได้ต้องอยู่ในตาราง · คอลัมน์หัวใจคือ **status กับ quiz_passed_at** ซึ่งเป็นผลการตัดสินตามกฎ ≥7/10 ณ ตอนนั้น ถ้าคำนวณใหม่ทุกครั้ง แล้ววันหนึ่งปรับเกณฑ์ ประวัติว่าเขาถูกปลดล็อกเมื่อไหร่จะเปลี่ยนตาม ตรวจย้อนหลังไม่ได้ · ส่วน words_learned กับ quiz_best_score ติดป้าย [cache] ชัดว่านับซ้ำได้จาก review_states กับ sessions เก็บเพราะหน้าเลือกหมวดอ่าน 5 การ์ดพร้อมกัน · คอลัมน์ที่เป็นตัวนับล้วน ๆ เช่นจำนวนครั้งทำควิซ ถอนออกแล้ว ใช้ query แทนครับ"

โครง: **ตาราง+คีย์ → กฎอาจารย์เอง → สถานะ ≠ ตัวนับ → [cache] แยกป้าย → ของที่ซ้ำจริงถอนแล้ว**

## ข้อ 5: "ผมร่างตารางกลาง หมวด-คำ-ผู้ใช้ ให้แล้ว ทำไมผังไม่มีตารางกลาง หมวด↔คำ"
⚠️ ห้ามพูด "ไม่จำเป็นเท่าไหร่" — ต้องมีกฎรองรับ
> "เพราะ หมวด↔คำ เป็น **1 ต่อหลาย** ครับ คำ 1 คำสังกัดหมวดเดียว หฤทัยเคาะแล้ว 300 คำไม่ซ้ำหมวด จึงใช้ช่อง FK **words.category** พอ · ตารางกลางจำเป็นเฉพาะคู่**หลายต่อหลาย** ซึ่งเรามี 3 ตัว: sentence_words, item_skills, form_items · ส่วน **ผู้ใช้↔หมวด** ที่อาจารย์ร่าง อันนั้นหลายต่อหลายจริง เรามีแล้วคือ category_progress · คำที่โผล่หมวดอื่นได้ผ่านประโยค (sentence_words) · อนาคตอยากสอนคำเดียวซ้ำหลายหมวดค่อยเพิ่ม word_categories ครับ"

โครง: **1:N → FK ช่องไหน → M:N 3 ตัว → ส่วนของอาจารย์เรามีแล้ว → ทางเผื่ออนาคต**

## ข้อ 6: "คำอธิบาย 'พลาดแบบคนไทย' มาจากไหน จะเขียนให้ครบทุกคนได้ไง ตรงไหนใช้ AI"
⚠️ อย่าเปิดด้วย "ยังไม่ได้ตรวจครับ" — พูดเป็นกระบวนการ (แต่ต้องเร่งหฤทัยตรวจจริง ค้างตั้งแต่ 12 ก.ค.)
> "แบ่ง 3 ชั้นครับ · **ถูกหรือผิด** ตรวจด้วยกฎเทียบเฉลยตายตัว ไม่ใช้ AI · **ผิดเพราะอะไร** มาจาก thai_l1_catalog คลังจุดผิดคนไทย 15 จุด เขียนจากงานวิจัยที่ตรวจแหล่งแล้ว และ**ตัวลวงในข้อสอบแต่ละตัวผูกกับจุดผิด 1 จุด** ตอบผิดตัวไหนระบบชี้คำอธิบายจุดนั้นได้ทันที **จึงเขียนแค่ 15 ชิ้น ไม่ได้เขียนรายคน** ทุกชิ้นผ่านหฤทัย (HSK 5) ตรวจก่อนขึ้นจริง · **ควรทำอะไรต่อ** แต่ละคนไม่เหมือนกัน เขียนล่วงหน้าไม่ได้ ตามที่อาจารย์แนะนำจึงให้ Gemini แต่งสดจากตัวเลข mastery ไม่เก็บลง DB เลยตัดตาราง recommendations ครับ"

โครง: **rule → catalog 15 (ตัวลวงผูกจุดผิด = ไม่ต้องเขียนรายคน) → Gemini แต่งสดตามที่อาจารย์แนะ**
จำ: ข้อ↔จุดผิด**ไม่ใช่ 1:1** — ข้อผูกหลายทักษะผ่าน item_skills · ตัวลวงแต่ละตัวผูกจุดผิดได้ตัวละ 1 (items.distractor_rationale) · จุดผิด 15 จุด = ทักษะ 15 ตัวใน 23

## ข้อ 7: "ผมหาเส้น items → words ไม่เจอ ข้อสอบข้อหนึ่งวัดคำไหน รู้ได้ไง"
> "เส้นนั้นไม่มีครับ **ตั้งใจไม่ทำ** เพราะข้อสอบในคลัง items **วัดทักษะ ไม่ได้วัดคำ** ผูกทักษะผ่าน item_skills และผูกหมวดผ่าน items.category · การติดตาม**รายคำ**เกิดในกิจกรรมฝึกซึ่ง**ระบบปั้นข้อสดจากคำ** (บัตรคำ ฟังเลือก จับคู่) ไม่ได้อยู่ในคลัง items แต่บันทึกลง attempts โดยชี้ **attempts.word_id** และสถานะความจำรายคำอยู่ที่ **review_states** ของ FSRS · 'นาย A แม่นคำ 买 ไหม' ตอบจาก review_states · 'นาย A แม่นทักษะฟังไหม' ตอบจาก mastery_snapshots · อนาคตอยากรู้ว่าข้อไหนใช้คำไหน ค่อยเพิ่ม item_words แต่ตอนนี้ตัดเพื่อลดงานแท็กคำทุกข้อครับ"

โครง: **ตั้งใจไม่มี → ข้อสอบวัดทักษะ → รายคำอยู่ฝั่งฝึก → คนละคำถาม คนละตาราง → ทางเผื่ออนาคต**
⚠️ อย่าพูด "attempts ชี้ได้ 3 ทาง" ลอย ๆ — ต้องบอกว่าเพราะแหล่งของข้อมี 2 แบบ (ข้อจากคลังที่ผ่านตรวจ vs ข้อที่ปั้นสดจากคำ/ประโยค)
